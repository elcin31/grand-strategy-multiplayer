Pinned Skia2.6.2 `RNSkView::requestRedraw` sets a pending redraw flag, then calls `runOnMainThread`. The existing JNI context queues tasks and sets `_mainThreadDispatchScheduled`. However, Java `PlatformContext.notifyTaskReady` synchronously drains that queue when its caller already runs on the UI thread. Therefore a request originating in the current gesture/animation can render before that callback publishes further values, rather than retain one pending redraw until the UI callback completes. This source-level behavior is confirmed; the contribution to the user's residual stutters is not established.

The experiment always posts the existing queue drain through its existing main-thread Handler. JNI queue, native view ownership, GL/EGL, surfaces, geometry, recorder lifecycle and caches are unchanged. Main-thread callbacks serialize execution and retain the latest published picture. No rendering worker thread, extra image, surface or cache is introduced. Source/hash drift and partial edits fail before patch writes. An execution marker is logged only after the first successful posted native callback; startup QA requires that marker in the live APK process, preserving raw old-process upgrade logs.
